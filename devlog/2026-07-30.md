  * `app/api/auth/forgot-password/route.ts` (Changed to use `hashed_token` instead of `action_link`)

#### 2. Technical Changes & Implementations
* **Files Modified/Created:** 
  * `app/api/auth/forgot-password/route.ts`
  * `app/reset-password/page.tsx`
* **Summary of Changes:**
  * **Root Cause:** `generateLink()` returns an `action_link` pointing to `supabase.co/auth/v1/verify?...&redirect_to=...`. Supabase's server only redirects to URLs whitelisted in the dashboard's Site URL / Redirect URLs config. Since localhost isn't whitelisted, the user always landed on `tailora.ng`'s landing page.
  * **API Route Fix:** Extracted `data.properties.hashed_token` from `generateLink()` and built a direct app link: `${origin}/reset-password?token_hash=xxx&type=recovery`. This bypasses Supabase's redirect server entirely — the email link goes straight to the user's app.
  * **Reset-Password Page Rewrite:** On mount, reads `token_hash` and `type` from URL query params. Calls `supabase.auth.verifyOtp({ token_hash, type: 'recovery' })` to establish a recovery session client-side. Added loading spinner during verification, error state with "Request New Reset Link" button for expired/invalid tokens, and signs the user out after successful password update so they log in fresh.

* **Issue Encountered:** Password reset link always redirected to hosted site (tailora.ng landing page) instead of the reset-password form.
* **Root Cause:** The `action_link` from `generateLink()` goes through Supabase's auth verification server, which only redirects to whitelisted URLs. Localhost is not whitelisted.
* **Resolution:** Bypassed Supabase's redirect entirely by sending the `hashed_token` directly in a link to our own app, then verifying it client-side with `verifyOtp`.
